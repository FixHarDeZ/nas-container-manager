# n8n

Shared workflow automation for the whole NAS. Any stack can be orchestrated from
here — n8n reaches services over the host's published LAN ports, so a stack
becomes callable the moment it is up, with no per-stack network config.

Split out of `secretary/` (was `secretary-n8n`) so it is no longer tied to the
lifecycle of one stack.

## Service

| Service | Container | Port (host→container) | RAM limit | Notes |
|---|---|---|---|---|
| n8n | n8n | 5678→5678 | 1.5G | Basic auth. External via Synology RP :15678 |

## Reaching other stacks

Workflows call `http://host.docker.internal:<published-port>/...`, resolved via
`extra_hosts: host.docker.internal:host-gateway`. Example (secretary RAG):

```
http://host.docker.internal:5065/query
http://host.docker.internal:5065/ingest-trigger
```

A docker DNS name like `secretary-query` only works inside that stack's own
compose network and will **not** resolve from here.

## Volume

| Volume | NAS path |
|---|---|
| n8n_data | `/volume2/docker/n8n/n8n_data` |

Moved here from `/volume2/docker/secretary/n8n_data` during the 2026-09-08
stack split — a rename within volume2, so atomic and no copy. It holds the
workflows, the credentials, and the encryption key that decrypts them. If n8n
ever starts against an empty `.n8n` it generates a new encryption key and every
stored credential becomes permanently undecryptable, so verify the directory is
non-empty before starting the container.

`scripts/deploy.sh` chowns this directory to `1000:1000` because the n8n image
runs as `node:node`.

## Env

`n8n/.env` is generated by `make secrets` from `secrets.manifest.yaml`.

| Variable | Used by |
|---|---|
| `N8N_BASIC_AUTH_USER` / `N8N_BASIC_AUTH_PASSWORD` | container basic auth |
| `N8N_WEBHOOK_URL` | public webhook base URL (Telegram etc.) |
| `N8N_API_KEY` | `scripts/n8n_export.sh` / `n8n_import.sh` only |

Vault paths remain `stacks.secretary.n8n.*`.

### Two URLs, two reverse-proxy entries

**Telegram registers webhooks only on ports 80, 88, 443 and 8443.** Anything
else fails `setWebhook` with `Bad Request: bad webhook`, the workflow never
finishes activating, and the bot goes quiet with nothing visible on the Telegram
side. That constraint is why the editor and the webhook are split:

| Variable | Value | Reverse proxy entry |
|---|---|---|
| `N8N_EDITOR_BASE_URL` | `https://<domain>:15678` | port-based, what people open in a browser |
| `N8N_WEBHOOK_URL` | `https://n8n.<domain>` | hostname-based on :443, what Telegram POSTs to |

Both entries must exist in DSM. Only :443 and :15678 are forwarded at the
router — 80, 88 and 8443 are not — so :443 is the only port Telegram can use
without a router change. Forwarding 8443 would allow collapsing both back onto
one hostname.

n8n only tells Telegram (and any other webhook provider) where to POST **when a
workflow is activated**, so changing this variable does not move an already
registered webhook. After the value changes, deactivate and reactivate every
workflow with a webhook trigger, or the provider keeps POSTing to the old URL
and the trigger goes silent with no error anywhere.

## Workflow backup

Workflow JSON files in `workflows/` are git-tracked.

```bash
# Export all workflows from the live instance into n8n/workflows/
./scripts/n8n_export.sh

# Import all workflows back into n8n (upsert by name)
./scripts/n8n_import.sh

# Import a specific workflow file
./scripts/n8n_import.sh n8n/workflows/Secretary_Bot__syPPm4qxmVNENC9U.json
```
